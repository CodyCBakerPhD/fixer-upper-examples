### Consolidation

#### CON-1 — `ex2.py` spreads every mode across a "compute" block and a "return" block

- **Location**: `02/ex2.py:11-92`. For example, `variance` runs at `28-29`,
  `40-43` and `83-86`. `fit` runs at `11-13`, `40-43`, `45-58` and `87-88`.
  `mode` runs at `17-23` and `75-82`.
- **Issue**: Readers have to follow each mode through the whole function. The
  conditions that guard shared intermediates (`mode == 'mean' or mode ==
  'variance'` at `28`, `mode == 'variance' or mode == 'fit'` at `40`) are a
  dependency graph written by hand, and they are wrong for `fit` (NV-1). This
  structure is behind ruff PLR0912 (28 branches > 12), PLR0915 (58
  statements > 50) and PLR1714 (`28`, `40`). It is also why the TASK's
  `"stdev"` mode would need edits in three places.
- **Proposed change**: Handle `fit` first and move it into `_linear_fit(points)`.
  Then compute `n = len(x)` and `total = sum(x)` once for the 1-D modes, and
  give each mode a single branch that returns immediately. Median and mode
  get small helpers. The full trial version is in [Appendix A](#appendix-a--proposed-shape-of-02ex2py).
  With this shape, `"stdev"` becomes a two-line branch next to `variance`.
- **Confidence it's safe**: **Medium**. It depends on NV-1 being fixed first,
  because without that fix every `fit` call raises and there is no behavior
  to preserve. Compared with `ex2.py` plus the NV-1 fix, the trial version
  matched on 224 of 234 snapshot lines, bit for bit, including `fit`, NaN
  and cancellation-prone inputs. The 10 lines that differ are all error
  paths:
  - `range` on `[]` raises `ValueError` instead of `IndexError` (this comes
    from CON-3).
  - `mode` on 2-D data still raises `TypeError`, but the message changes from
    "unhashable type: 'list'" to "unsupported operand type(s) for +", because
    `sum()` now runs before the counting.
- **Verification**: snapshot diff against the NV-1 baseline shows only those 10 lines; `ruff check --isolated --select PLR0912,PLR0915,PLR1714 02/ex2.py` is clean.

#### CON-2 — `ex2.py` hand-rolls `collections.Counter` and `most_common`

- **Location**: `02/ex2.py:17-23` (counting loop) and `02/ex2.py:76-81` (finding the most common value)
- **Issue**: Thirteen lines across two blocks reimplement
  `Counter(x).most_common(1)[0]`, and need a `# type: ignore` (`82`)
  because of how `the_mode = None` is initialised. `most_common` breaks
  ties the same way (first value seen), because `heapq.nlargest(1, …)`
  calls `max()`, which keeps the first maximal item, just like the strict
  `>` at `79`.
- **Proposed change**:
  ```python
  def _mode(x: list[float]) -> tuple[float | None, int]:
      if not x:
          return (None, 0)          # ex2.py's result for empty input
      return Counter(x).most_common(1)[0]
  ```
- **Confidence it's safe**: **High**. Dictionary keys and equality behave the
  same as in the original. The empty-input result is kept by the guard. In
  the trial, the snapshot was identical, including the all-tied input
  `[5.0, 1.0, 3.0]` (the first value wins) and the NaN input.
- **Verification**: snapshot diff is empty.

#### CON-3 — `ex2.py` hand-rolls `min()`/`max()` and shadows both builtins

- **Location**: `02/ex2.py:60-67`
- **Issue**: An index loop (`for i in range(len(x))`) reimplements
  `min(x), max(x)`. It assigns to local variables named `max` and `min`
  (ruff A001 ×4), which hides the builtins for the rest of the function, and
  ruff PLR1730 ×2 suggests the builtin replacement.
- **Proposed change**: `return (min(x), max(x))` in the `range` branch.
- **Confidence it's safe**: **Medium**. The builtins compare in the same
  direction as the loop (`item > current` / `item < current`), and the first
  extreme value wins, so every non-empty input gives the same result
  (snapshot-identical, NaN included). On `[]` the exception changes from
  `IndexError: list index out of range` to `ValueError: min() iterable
  argument is empty`. Keeping it exactly would need an explicit
  `if not x: raise IndexError(...)`, which isn't worth having. Settle it
  together with NV-4.
- **Verification**: The snapshot diff shows only the two `range` lines for `[]`.

### Cleanup

#### CL-1 — `ex2.py`'s annotations don't describe what `summarize` takes or returns

- **Location**: `02/ex2.py:8` (`mode` is unannotated), `02/ex2.py:10` (return annotation), `82` (`# type: ignore`), `92` (`return None`)
- **Issue**: `-> float | tuple[float, float]` leaves out `None` (unknown
  modes, `92`) and `(None, 0)` (empty `mode`, `77`/`82`). The `# type: ignore`
  hides the second omission. mypy reports 7 errors: `index` at `12`, `13`,
  `assignment` at `15`, `50`, `57`, `var-annotated` at `18`, and
  `return-value` at `92`. The two at `50` and `57` come from `0`
  initialisers that later hold floats.
- **Proposed change**: Annotate `mode: Literal["sum", "mean", "median", "mode", "variance", "range", "fit"]`.
  Return `float | tuple[float, float] | tuple[float | None, int] | None`.
  Wrap the two uses of `data` in `cast(...)` (as in CL-5). Annotate the
  accumulators (`slope_numerator: float = 0`) rather than changing them to
  `0.0`, because `0.0` would turn exact integer arithmetic on int data into
  float arithmetic. Then delete the `# type: ignore`. The unwieldy return
  type is honest, and it is the argument for NV-5.
- **Confidence it's safe**: **High**. Annotations and `cast` do nothing at
  runtime. In the trial (with CON-1 to CON-3), mypy printed "Success" with
  `--warn-unused-ignores`.
- **Verification**: `mypy --warn-unused-ignores 02/ex2.py` reports no errors, and the snapshot is unchanged.

#### CL-2 — `ex2.py` loops by index and builds throwaway lists

- **Location**: `02/ex2.py:48-50` and `55-57` (`for i in range(len(...))`), `42-43` (single-use `x_xi_diff_sq` list), `53` (`sum([... for ...])`)
- **Issue**: Index loops over two parallel lists are what `zip` is for. The
  list built at `42` is consumed once, and `sum([...])` materialises a list
  only to throw it away.
- **Proposed change**: Write `for dx, dy in zip(x_dev, y_dev): slope_numerator += dy * dx`
  (and the same for `sum_xy`), `sum_sq = sum(d**2 for d in x_dev)`, and
  `sum_x_sq = sum(item**2 for item in x)`. **Keep the `+=`
  accumulation.** Since Python 3.12, `sum()` of floats uses compensated
  (Neumaier) summation. Replacing the two `+=` loops with `sum(...)`
  changed the `fit` result's last digits in 7,753 of 20,000 random point
  sets (Python 3.13, tried).
- **Confidence it's safe**: **High**. The elements are the same and are added
  in the same order. Both `sum(list)` and `sum(generator)` use the same
  algorithm. The parallel lists always have equal length because they are
  built from the same points. In the trial, the snapshot was identical.
- **Verification**: snapshot diff is empty.

#### CL-5 — `ex3.py`'s `summarize` never narrows `data`

- **Location**: `03/ex3.py:78`, `83`
- **Issue**: `data: list[float] | list[list[float]]` is passed straight to

#### NV-1 — `02/ex2.py` crashes in `fit` mode

- **Why it is not a quality change**: The fix turns an exception into a result.
- **Decision needed**: Was this planted for participants to find? Neither

#### NV-2 — The closed-form intercept is numerically unstable

- **Location**: `02/ex2.py:58` and `03/ex3.py:67` (the same formula). It is also carried into `02/ex2-soln.py:65` and `03/ex3-soln.py:111`.
- **Observation** (observed): `intercept = (Σy·Σx² − Σx·Σxy) / (n·Σx² − (Σx)²)`
  subtracts nearly equal large numbers when the x values are far from 0.
  The test used 10 points with y = 3 + 2x and x = off + i. The formula is
  exact up to off = 1e6. At off = 1e8 it returns −214,843,746.67 where the
  exact value is −199,999,997.0, which is 7.4% off. `y_mean - slope * x_mean`
  gives the exact value. The slope is fine, because it is already computed
  from centred deviations (`02/ex2.py:41-51`).
- **Why it is not a quality change**: The fix returns different floats: the
  last bits change for well-conditioned data, and large differences appear
  for ill-conditioned data.
- **Decision needed**: Should "fit" keep its exact historical numbers, or
  switch to `y_mean - slope * x_mean`? Switching also drops two passes over
  the data (`sum_x_sq` and `sum_xy`, at `02/ex2.py:53-57` and `03/ex3.py:61-62`),
  which serves exercise 3's "avoid repeating work" goal directly.

#### NV-3 — Malformed input is rejected by accident, or not at all

- **Location**: `02/ex2.py:26` and `92`; `03/ex3.py:38` and `80`
- **Observation** (observed via the snapshot):
  - **`ex2.py`.** Non-numeric data and 2-D data in a 1-D mode are rejected
    only because `total = sum(x)` happens to run for every mode, so callers
    get `TypeError: unsupported operand type(s) for +: 'int' and 'list'`.
    For `mode` the counting loop runs first, so the error is "unhashable
    type". Unknown modes return `None` silently, and that includes
    `"stdev"`, the mode the TASK asks for.
  - **`ex3.py`.** The 2-D guard checks only `isinstance(data[0], list)`, so
    tuple points get through:
    - `summarize([(1.0, 2.0), (2.0, 4.0)], "range")` returns
      `((1.0, 2.0), (2.0, 4.0))`, because tuples compare lexicographically.
    - `"mode"` returns `((1.0, 2.0), 1)`.
    - `"mean"` fails deep inside `statistics` with "can't convert type
      'tuple' to numerator/denominator".

    In `ex2.py` all of these inputs raised `TypeError`, so for `range` and
    `mode` the exercise-2 refactor turned an error into a wrong answer.
    Unknown modes raise a bare `KeyError: 'bogus'`.
- **Why it is not a quality change**: Explicit validation changes which
  exceptions are raised, and when.
- **Decision needed**: The error contract: which exception is raised, and
  whether a tuple or other `Sequence` counts as a point. `ex3.py`'s new API
  (the exercise-3 task) is the natural place to set it. Note that "unknown
  mode returns `None`" is legacy behavior that callers may rely on.

#### NV-4 — Empty and one-element inputs fail differently in each mode

- **Location**: `02/ex2.py:25-90`, `03/ex3.py:24-34`
- **Observation** (observed):

  | input | `sum` | `mean` | `median` | `mode` | `variance` (sample) | `range` |
  |---|---|---|---|---|---|---|
  | `[]`, ex2.py | `0` | ZeroDivisionError | IndexError | `(None, 0)` | ZeroDivisionError | IndexError |
  | `[]`, ex3.py | `0` | StatisticsError | StatisticsError | IndexError | StatisticsError | ValueError |
  | `[7.0]`, ex2.py | `7.0` | `7.0` | `7.0` | `(7.0, 1)` | ZeroDivisionError | `(7.0, 7.0)` |
  | `[7.0]`, ex3.py | `7.0` | `7.0` | `7.0` | `(7.0, 1)` | StatisticsError | `(7.0, 7.0)` |

  A one-point `fit` raises `ZeroDivisionError` in `ex3.py`, and in
  `ex2.py` too once NV-1 is fixed.
- **Why it is not a quality change**: Making these consistent changes return values or exception types.
- **Decision needed**: What `summarize` should do with too-short input. CON-3's empty-`range` difference belongs to this decision.

#### NV-5 — The return shape depends on `mode`

- **Location**: `02/ex2.py:6-10`, `03/ex3.py:72-76`
- **Observation**: Depending on `mode`, one function returns a float, `(low, high)`,
  `(value, count)`, `(intercept, slope)` or `None`. `is_sample` only matters for
  `variance` and `stdev`, and other modes ignore it silently. CL-1's honest
  return annotation
  (`float | tuple[float, float] | tuple[float | None, int] | None`) shows
  what callers have to handle.
- **Why it is not a quality change**: It is the public interface.
- **Decision needed**: Both TASK texts keep this interface for now, and
  exercise 3 asks for a new API alongside it. That new API is where a typed
  return (one field per statistic) would fix this, as the `# todo
  TypedDict?` in the provided solution hints.

### Exercise 2: Appendix A vs `02/ex2-soln.py`

**Where the two agree.** Both move `fit` into its own function
(`ex2-soln.py:45-67`, matching CON-1's `_linear_fit`). Both use

Both give `mode` a `Literal` type (`14-17`, CL-1).

**Where the provided solution is better:**

- Its `STATS` table (`22-32`) is more compact than CON-1's chain of
  `if`/`return`. Adding `stdev` becomes a one-entry change, and it avoids the
  PLR0911 warning (9 returns) that Appendix A still triggers.
- Raising `ValueError("2-d data supplied to 1-d statistic")` (`78-79`) is a
  better error than `ex2.py`'s incidental `TypeError` from `sum`. It is one

**Where I think this review's approach is better:**

- **It preserves behavior.** `ex2-soln.py:1` says the solution doesn't alter
  the interface, but it does change behavior:
  - `statistics.mean` and `pvariance` return `int` for int data:

  exercise, I think the behavior changes should be either avoided or listed.
- **It keeps the formulas visible.** Appendix A keeps `total / n` and

  intermediates, and `03/ex3-soln.py:1-6` has to walk back exercise 2's

### Exercise 3: this review's reading of `ex3.py` vs `03/ex3-soln.py`

The solution's `OneDStats` class, with cached properties that chain sum →
mean → squared deviations → variance → stdev (`ex3-soln.py:26-86`), is the
right shape for "avoid repeating work". `linear_fit` reusing
`x.total_variation` (`103`) is the payoff. Here is what I would do
differently, in order of impact:

1. **Accept ints.** `_standardize_structure` tests `type(data[0]) == float`
   (`158`, ruff E721). As a result, `get_stats([1, 2, 4], ["mean"])` raises
   `ValueError: Data list expected to be two data series.`, a misleading
   message, and int points fail too. `ex3.py`'s `summarize` accepts both, so
   this is a regression in the new API. `isinstance(v, (int, float))` would
   fix it.
2. **Validate statistic names.** The `getattr` dispatch (`129`, `150`)
   accepts any attribute name. `get_stats(d, ["data"])` returns the raw list,
   `summarize(d, "counts")` returns a `Counter`, and `["__class__"]` returns
   the class. `ex3.py`'s `STATS` lookup at least rejects unknown names.
   Checking against `typing.get_args(T_stats)` would close this.
3. **Use the cached means for the intercept.** `y.mean - slope * x.mean`
   fixes NV-2 and drops the `sum_x_sq` and `sum_xy` passes (`105-106`).
   That is more shared work, which is the exercise's goal.
4. **Make the two APIs agree on 2-D data.** `summarize(points, "mean")`
   raises an error, but `get_stats(points, ["mean"])` returns the mean of
   the y values. The rule marked "(unstated?)" at `ex3.py:7` is applied to
   only one of the two APIs.
5. **Keep the legacy API stable.** `ex3-soln.py`'s `summarize` reverses
   `ex3.py`'s int/float results (`4` back to `4.0`) and its error types
   (`StatisticsError` back to `ZeroDivisionError`). So the legacy API's
   behavior changes once in exercise 2 and again in exercise 3.
6. **Smaller items:**
   - `Callable` and `Mapping` are imported but unused (`16`), left over
     after dd20e38 removed `STATS`.
   - `mean` divides by `len(self.data)` where every other property uses
     `self.n` (`40`).
   - mypy reports 5 errors.
   - `OneDStats` stores the caller's list without copying it (`31`), so
     mutating that list leaves the cached values stale.

## Appendix A — proposed shape of `02/ex2.py`

This is the trial file behind CON-1, CON-2, CON-3, CL-1, CL-2, CL-3 and
DUP-1, with the NV-1 fix assumed. It is formatted with `ruff format`,
passes mypy, and matches `ex2.py` plus the NV-1 fix on the snapshot except
for the 10 error-path lines listed under CON-1. It does not add `"stdev"`:
that is the exercise.

```python
from collections import Counter
from typing import Literal, cast

Mode = Literal["sum", "mean", "median", "mode", "variance", "range", "fit"]


def summarize(
    data: list[float] | list[list[float]],
    mode: Mode,
    is_sample: bool = True,
) -> float | tuple[float, float] | tuple[float | None, int] | None:
    if mode == "fit":
        return _linear_fit(cast(list[list[float]], data))

    x = cast(list[float], data)
    n = len(x)
    total = sum(x)  # every 1-d mode starts here, so non-numeric data raises TypeError

    if mode == "sum":
        return total
    if mode == "mean":
        return total / n
    if mode == "median":
        return _median(x)
    if mode == "mode":
        return _mode(x)
    if mode == "variance":
        mean = total / n
        sum_sq = sum((item - mean) ** 2 for item in x)
        if is_sample:
            return sum_sq / (n - 1)
        return sum_sq / n
    if mode == "range":
        return (min(x), max(x))
    return None


def _median(x: list[float]) -> float:
    x = sorted(x)
    half = len(x) // 2
    if len(x) % 2 == 1:
        return x[half]
    return (x[half] + x[half - 1]) / 2


def _mode(x: list[float]) -> tuple[float | None, int]:
    if not x:
        return (None, 0)
    return Counter(x).most_common(1)[0]


def _linear_fit(points: list[list[float]]) -> tuple[float, float]:
    x = [point[0] for point in points]
    y = [point[1] for point in points]
    n = len(points)
    sum_x = sum(x)
    sum_y = sum(y)
    x_mean = sum_x / n
    y_mean = sum_y / n

    x_dev = [item - x_mean for item in x]
    y_dev = [item - y_mean for item in y]
    sum_sq = sum(d**2 for d in x_dev)
    # += rather than sum(): sum() of floats is compensated since Python 3.12
    slope_numerator: float = 0
    for dx, dy in zip(x_dev, y_dev):
        slope_numerator += dy * dx
    slope = slope_numerator / sum_sq

    sum_x_sq = sum(item**2 for item in x)
    sum_xy: float = 0
    for xi, yi in zip(x, y):
        sum_xy += xi * yi
    intercept = (sum_y * sum_x_sq - sum_x * sum_xy) / (n * sum_x_sq - sum_x**2)
    return (intercept, slope)
```
